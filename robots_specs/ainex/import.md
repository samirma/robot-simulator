# AiNex — URDF and MuJoCo import notes

`model.xml` is a **derived** MuJoCo model, not manufacturer-provided. Hiwonder publishes no
MJCF for the AiNex. Everything below was established on 2026-09-30 from the pinned sources;
no figure here was measured on a real robot.

## `ainex.urdf` — how it was produced

Upstream ships no `.urdf`, only `src/ainex_simulations/ainex_description/urdf/ainex.urdf.xacro`
(which includes `materials.xacro` and `transmissions.xacro`; the vendor's `display.launch`
and `imu.launch debug:=true` load exactly this file as `robot_description`). `ainex.urdf` is
its expansion:

1. Copy the four `*.xacro` files of `ainex_description/urdf/` at the pinned revision, replacing
   `$(find ainex_description)` with the copy's directory (xacro's `$(find)` needs a ROS
   install).
2. Run `xacro ainex.urdf.xacro > ainex.urdf` (xacro 2.1.1 from PyPI).
3. Replace xacro's four-line "autogenerated" banner (it names the temporary path) with a
   provenance comment. Nothing else is changed; mesh URIs stay
   `package://ainex_description/meshes/<link>.STL`, which resolve to
   `robots_specs/ainex/meshes/` (the robot folder stands for the package root).

`ainex.xacro` (URDF + `gazebo.xacro`) was not used: its extra content is Gazebo-only.
Result: 28 links, 27 joints (24 revolute + `base_link_to_body`, `camera`, `imu` fixed),
total mass 2.347 kg. It is joint-for-joint identical (names, types, origins, axes, limits)
to the previous revision of this repository's `robots_specs/ainex/ainex.urdf`.

## Conversion steps (`model.xml`)

`robots_specs/tools/models/ainex.py` (standard library `xml.etree` + the URDF) generates the
model and reproduces `model.xml` byte for byte (its defaults are the home height 0.2029 m and
body pitch 0.2609658522284916 rad described below). Its rules are:

1. One `<body>` per URDF link, named after the link, at its parent joint's `origin`
   (rpy converted to a quaternion); fixed joints become welded child bodies (`camera_link`,
   `imu_link`, `body_link` under `base_link`).
2. One `hinge` per revolute joint, named after the joint, with the URDF axis and
   `range = [lower, upper]` (±2.09 rad on every joint).
3. Each URDF `<inertial>` as `<inertial pos mass fullinertia>` (values copied).
4. Each URDF visual mesh as a visual geom (`group 2`, no contact) with its URDF material
   colour; each URDF collision mesh as a collision geom (`group 3`; MuJoCo collides the
   mesh's convex hull). Mesh `file`s are `meshes/<link>.STL` relative to the robot folder.
5. Adaptations 1–7 below.
6. Validation: `mujoco.MjModel.from_xml_path("robots_specs/ainex/model.xml")` (MuJoCo
   3.14.0) loads it (29 bodies, 25 joints incl. the freejoint, 24 actuators, 1 camera,
   1 site). In a wrapper adding only a floor plane, starting from keyframe `home` with
   `ctrl = home`, 3 s of simulation (timestep 0.002 s) leave the robot standing: body_link
   moves 1.8 mm forward and 1.0 mm down, its up-axis stays at the home lean
   (0.273, 0, 0.962), the largest joint deviation is 0.0115 rad, and only the soles touch
   the floor. `head_pan` → 0.5 rad and `head_tilt` → −0.3 rad are reached within 0.001 rad
   in 2 s while standing.

## Adaptations (differences from the URDF)

1. **Freejoint** `root` on `base_link` (the robot walks; nothing fixes it to the world).
2. **Foot soles.** A box `r_sole`/`l_sole` (0.1351 × 0.076 × 0.004 m) under each
   `*_ank_roll_link`, fitted to the axis-aligned bounds of the link's own mesh
   (x −0.0379…0.0972, y as the mesh, bottom z −0.0231), `condim 4`, friction 1.5 (the
   vendor's Gazebo value for the ankle-roll links in `gazebo.xacro`; the real sole friction
   is not documented — estimate), `priority 1`, stiff `solref 0.004 1`. The URDF mesh
   collision is kept as well.
3. **Contact exclusions** for `r/l_hip_yaw_link`–`r/l_hip_pitch_link` and
   `r/l_knee_link`–`r/l_ank_roll_link`: the convex hulls of these non-adjacent links already
   overlap (≈21 mm) in the URDF's zero pose, an artefact of hull collision, not a real
   contact.
4. **Actuators** (all estimates, see below): one `position` actuator per revolute joint,
   named after it, command in rad, `ctrlrange` = joint range.
5. **Head camera.** `<camera name="camera">` (the image `frame_id` of the boot) mounted on
   `head_tilt_link` at xyz (0.038068, 0.018573, 0.016398) with URDF-link axes (x forward,
   z up; MuJoCo `xyaxes="0 -1 0 0 0 1"`), `fovy` 83.267°, `resolution` 640×480. The URDF puts
   `camera_link` on `body_link` at (0.043014, 0, 0.152356); the camera is physically in the
   2-DOF head (docs: "2-DOF HD camera"), so the model attaches it to the head at the pose
   that coincides with `camera_link` when head_pan = head_tilt = 0 (checked: world positions
   equal at the home pose). `camera_link` itself is kept as a welded body.
6. **IMU site** `imu_link` at the URDF `imu` joint pose, with `accelerometer`, `gyro` and
   `magnetometer` sensors on it (the boot publishes all three).
7. **Keyframe `home`** = the boot standing pose, which is also the model's default body
   pose: joints = `ainex_kinematics/config/init_pose.yaml` (sent by ainex_controller at boot
   over 1 s), `ctrl` = the same, root pitched +0.26097 rad about y so both soles are flat
   (the init pose leaves the torso leaning 15° forward of the feet, matching the gait's
   `hip_pitch_offset` 15°), root height 0.2029 m (soles 0.5 mm above z = 0). With joints at
   zero (qpos0) the legs are straight and the robot is not balanced; use `home`.
   **Arms (changed 2026-10-02):** `home` is the spawn pose, so its arms are not the boot's
   (`init_pose.yaml` raises them, shoulder roll ±1.293 with the elbows yawed ±1.926) but
   relaxed down at the sides like a person at rest: shoulder roll -1.45 (left) and +1.45
   (right), shoulder pitch, elbow pitch and elbow yaw 0. Legs, head and root are the boot's.

## robot_description versus the model

The authoritative boot (`bringup.launch`) loads **no** `robot_description` and publishes no
TF, so there is no boot description to govern the model. Joint names on the wire are those
of `ainex_controller.py` `joint_id`, which equal the URDF names. Differences between the boot
controller and the URDF, recorded in `ros.yml` `model.robot_description`:

* **Angle ↔ servo mapping.** `pulse = init + angle · (±1000 / 240°)` with `init` and the
  direction (`min > max` = flipped) from `servo_controller.yaml`. With `init_pose.yaml`
  applied to the URDF the pose is a symmetric crouch with flat, parallel feet (after the root
  pitch of adaptation 7): no zero-offset conflict was found.
* **Reachable ranges.** The URDF allows ±2.09 rad everywhere; the servo pulse range 0–1000
  allows ±2.094 rad for `init 500` but `l_knee` [−1.005, 3.184], `r_knee` [−3.184, 1.005],
  `l_sho_pitch` [−0.524, 3.665], `r_sho_pitch` [−3.665, 0.524] rad. The model keeps the
  URDF ranges; the wire's commands are bounded by the intersection.

### Camera calibration

The boot loads its calibration from `/home/ubuntu/.ros/camera_info/head_camera.yaml`
(`usb_cam.launch#L15`), a file on the robot's SD image that is in no pinned source. The
manufacturer's field-of-view figures conflict: the official docs (chapter 1) give
"FOV 170°" for a 640×480 USB camera; retail listings give "120° wide-angle". The model uses
the documented 170° read as the diagonal of an equidistant fisheye lens,
f = 400 px / (85° in rad) = 270 px, rendered as a pinhole camera with zero distortion
(hfov 99.7°, vfov 83.27° = the MuJoCo `fovy`). The simulator publishes CameraInfo with this
K and P and zero D, consistent with the render. This is an estimate, not a calibration; a
real-robot calibration file should replace it when available.

### Camera pose

From the URDF `camera` joint (`ainex.urdf.xacro`), re-parented to `head_tilt_link` as in
adaptation 5. The optical axis is the link's +x; the boot publishes no camera TF.

## Items not established

* Real-hardware rates of the board IMU/magnetometer and battery reports (only the node's
  100 Hz loop cap is in the source), and every watchdog: all derived from source.
* Action-group files (`*.d6a`), LAB colour thresholds and the camera calibration file are
  not in any pinned source (see `ros.yml` `boot.data_files`).
* The gait engine (`walking_module.so`) and leg IK (`kinematics.so`) are closed aarch64
  Python 3.8 binaries; walking speed per parameter set is therefore not derivable from
  source.
